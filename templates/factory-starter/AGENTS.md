# Rules for agents working in this repo

This app was generated by the AI Real Solutions Factory from a customer's approved Site Spec.

## This is NOT the Next.js you know
Next.js 16: `proxy.ts` replaces `middleware.ts`; `params`, `searchParams` and `cookies()` are async.
Read `node_modules/next/dist/docs/` before using an API you are unsure of.

## How the app is put together
- `site.json` is the Site Spec (brand, pages, sections, entities, forms, automations, demo rows).
  Pages render from it through `lib/site-spec.ts` (`sanitizeSiteSpec`). Prefer changing `site.json`
  over hard-coding pages. Only the section types in `SECTION_TYPES` exist; add a new one in
  `lib/site-spec.ts` AND `components/Sections.tsx` together.
- Forms post to `app/api/forms/[key]/route.ts`, which checks values against the form's fields and saves
  through the `site_submit` RPC. Visitors never write tables directly.
- Signed-in staff (emails in `site_members`) see submissions; row-level security enforces it.
- Email goes through `lib/email.ts` (Resend). Secrets stay on the server: never `NEXT_PUBLIC_` a key.

## Rules
1. Every new table gets RLS in the same migration, with policies. Add a test for it in `supabase/tests/rls.sql`.
2. Migrations are new numbered files in `supabase/migrations/`; never edit one that has shipped.
3. Anything that sends to customers, spends money, deletes data or publishes needs a human approval step.
4. Keep `npm run check` and `npm run test:rls` passing. A change is done only when both pass, not when it looks done.
5. Keep the site usable on a phone (390px wide, no sideways scrolling) — the smoke tests check it.
6. Demo rows show only with `NEXT_PUBLIC_DEMO_MODE=true`. Never in production.
